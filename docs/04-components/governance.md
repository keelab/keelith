# 弹性治理与流量防护

在真实的分布式微服务网络中，网络抖动、机房断缆、下游数据库慢查询甚至流量突增都是不可避免的常态。如果不加防护，一个非核心节点的偶发延迟就会像多米诺骨牌一样迅速耗尽全链路的线程与连接资源，引发**级联雪崩（Cascading Failure）**。

Keelith 将经过生产检验的可用性算法沉淀在 `governance` 套件中，提供全方位的流量防护与自愈能力。

---

## 1. 治理策略组合防线与执行顺序

Keelith 提倡分层防护原则。从外到内，不同治理策略的装配与生效顺序如下：

```text

                                    ▼

                                    ▼
┌───────────────────────────────────────────────────────────────────────┐
│ 2. 速率限制 (Rate Limiting)                                           │

└───────────────────────────────────┬───────────────────────────────────┘
                                    │
                                    ▼

│ 3. 严格超时控制 (Timeout & Deadline Propagation)                      │
```

## 2. 核心治理能力深度剖析

### 2.1 超时传递 (Timeout Propagation)
在分布式调用中，如果第一跳设置了 5 秒，第二跳设置了 10 秒，那么当第一跳已经超时返回时，第二跳仍会在后台白白空耗资源。
Keelith 在传输层自动将 `Context Deadline` 序列化为协议头（如 gRPC 的 `grpc-timeout` 或 HTTP 的 `Request-Timeout`），下游服务解析后自动构建更短的本地 Context，保证**超时取消在全链路级联传播**。

### 2.2 重试预算 (Retry Budget) —— 终结重试风暴
传统的重试策略（如固定重试 3 次）是导致线上雪崩的最常见元凶。当服务 B 出现瓶颈变慢时，服务 A 发起 3 倍流量的重试，直接将服务 B 彻底打死。

Keelith 采用**基于滑动窗口的重试预算机制（Token Bucket Retry Budget）**：
- 只有常规请求成功时，才会往预算桶中注入“重试代币”。
- 重试请求必须消耗代币，**重试流量占正常请求的比例被严格锁定在安全阈值以下（例如 10%）**。
- 一旦下游故障率上升，重试预算会瞬间耗尽，框架自动停止发起重试，保护下游免遭流量二次碾压。

### 2.3 熔断器 (Circuit Breaker)
Keelith 内置的三态自适应熔断器：
- **Closed（闭合态）**：正常放行流量。持续统计时间窗口内的失败率（如 500、连接超时）。
- **Open（开启态）**：当失败率突破阈值（如 35%），熔断器开启，后续请求立即快速失败返回 `ErrCircuitOpen`，不发起真实网络调用。
- **Half-Open（半开态）**：经过休眠恢复期（如 5 秒）后，允许探针流量试探下游；若连续成功则恢复到 Closed，若依然失败则重新回到 Open。

### 2.4 并发隔离 (Bulkhead)
将应用内部的不同下游划分为独立“隔舱”：
```go
// 限制针对推荐服务的最大并发请求数为 50
// 即使推荐服务发生全量挂起，最多只占用 50 个并发槽位，绝不影响主流程订单下单！
bulkhead := bulkhead.New(bulkhead.Config{
    MaxConcurrent: 50,
    MaxWait:       100 * time.Millisecond,
})
```

## 3. 生产治理配置示例

结合 `client.Outbound`，为外部依赖装配完整的弹性策略：

```go
package main

import (
	"time"

	"github.com/keelab/keelith/client"
	"github.com/keelab/keelith/governance/dependency"
)

func BuildPaymentOutbound() (*client.Outbound, error) {
	return client.NewOutbound(client.OutboundConfig{
		Dependency: dependency.Config{
			Name: "payment-gateway",
			// 1. 严格超时
			Timeout: 3 * time.Second,
			// 2. 重试预算控制
			Retry: dependency.RetryConfig{
				MaxAttempts: 2,
				BudgetRate:  0.08, // 重试量不得超过正常流量的 8%
				BackoffBase: 100 * time.Millisecond,
			},
			// 3. 熔断器
			Breaker: dependency.BreakerConfig{
				FailureRate: 0.25,
				Window:      10 * time.Second,
			},
			// 4. 并发隔离
			Bulkhead: dependency.BulkheadConfig{
				MaxConcurrent: 100,
			},
		},
	})
}
```

> [!WARNING]
> **切勿在多层同时开启无界重试**：
> 如果接入网关、聚合服务和基础 RPC 客户端都各自独立配置了重试，最终一次用户点击可能触发 $3 \times 3 \times 3 = 27$ 次底层调用！使用 Keelith 时，建议只在最靠近调用发起的边缘层开启受控重试，或者仅在底层明确针对偶发幂等读操作开启重试。
